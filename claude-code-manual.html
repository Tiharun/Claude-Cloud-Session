클로드를 잘 쓰는 사람은 컨텍스트와 검증을 관리합니다

처음 구독한 사람이 오늘 바로 쓸 수 있도록, 클로드 코드(Claude Code)를 중심으로 요금제, 모델, 프롬프트, 사용량 절약, MCP, 자동화, 공부법까지 한 곳에 정리했습니다.

결론 먼저

  1. Pro는 "한 번에 한 작업, 짧고 깨끗한 세션", Max는 "여러 작업을 병렬로 맡기고 오래 돌리기"가 맞는 쓰임새입니다. 추론
  2. 클로드 코드의 기본 모델은 Opus 5.5, 기본 노력 수준은 medium입니다. 반복 구현은 Sonnet 5.5, 어려운 설계·디버깅은 Opus 5.5에서 노력 수준을 올리고, 몇 시간짜리 자율 작업은 Fable 5.1을 고려합니다. 사실 + 추론
  3. 결과 품질을 가장 크게 바꾸는 것은 클로드가 스스로 돌려 볼 수 있는 검증 수단(테스트, 빌드, 스크린샷)입니다. 사실
  4. 사용량을 가장 크게 좌우하는 것은 컨텍스트context의 크기입니다. 작업이 바뀌면 /clear, CLAUDE.md는 짧게, 조사·로그 분석은 서브에이전트에 맡깁니다. 사실
  5. 반복되는 절차는 스킬skill로, 반드시 일어나야 하는 일은 훅hook으로, 외부 서비스는 CLI 도구를 먼저 쓰고 없으면 MCP로 연결합니다. 사실

버전 주의. 클로드 코드는 매주 바뀝니다. 아래 내용은 Claude Code v2.1.28x 대 문서를 기준으로 합니다. 터미널에서 claude --version으로 버전을 확인하고, 오래됐다면 claude update를 실행하세요. Haiku 5.5는 v2.1.293 이상, Sonnet 5.5는 v2.1.284 이상, Opus 5.5는 v2.1.280 이상, Mod는 v2.1.287 이상(데스크톱 앱 내장판은 v2.1.286 이상)이 필요합니다. 사실

오늘 첫 30분 체크리스트

  1. 1
    설치·로그인 확인claude --version이 버전을 출력하면 설치 완료. 프로젝트 폴더에서 claude를 실행해 Pro 계정으로 로그인합니다. → 설치와 기본기
  2. 2
    사용량 화면 위치 익히기클로드 코드 안에서 /usage, 웹에서는 claude.ai의 Settings > Usage. 5시간 세션 한도와 주간 한도가 막대로 보입니다. → 요금제
  3. 3
    프로젝트 기억 파일 만들기/init으로 CLAUDE.md 초안을 만든 뒤 200줄 이하로 다듬습니다. → CLAUDE.md
  4. 4
    검증 명령 정해 두기테스트·린트·빌드 명령을 CLAUDE.md에 적어 두면 클로드가 스스로 확인하며 일합니다. → 코딩 특별 페이지
  5. 5
    권한 모드 이해하기Shift+Tab으로 수동 · 편집 자동 승인 · 계획 · 자동 모드를 오갑니다. 큰 작업은 계획 모드부터. → 권한 모드
  6. 6
    작업이 바뀌면 /clear이 습관 하나가 사용량과 품질을 동시에 지킵니다. → 사용량 절약
데스크톱 앱의 Code 탭을 쓴다면. 위 체크리스트의 명령과 단축키는 터미널 기준입니다. Code 탭에서는 설치가 필요 없고, /clear·/rename·Shift+Tab 같은 조작은 Claude 탭과 Code 탭의 대응표대로 바꿔 씁니다.

요금제

Pro와 Max, 각각 이렇게 씁니다

결론

  • 두 요금제 모두 클로드 코드를 포함하며, 웹·데스크톱·모바일·클로드 코드가 한 사용량 풀을 함께 씁니다. 사실
  • 차이는 사용량(5시간 세션당 Pro의 5배 / 20배), Fable 접근 방식, 혼잡 시간 우선 접근입니다. 사실
  • Pro에서는 컨텍스트를 아끼는 습관이 곧 생산성이고, Max에서는 병렬 세션·위임·장시간 자율 실행으로 늘어난 한도를 "시간"으로 바꾸는 것이 핵심입니다. 추론

모바일 앱 결제 가격은 플랫폼에 따라 다를 수 있습니다. Pro 연간 결제 중에 Max로 올리면, 남은 금액이 크레딧으로 이월되는 규칙이 있습니다(청구지 주소가 같아야 함). 사실

한도를 이해하는 세 가지 개념

  • 5시간 세션 한도session limit: 처음 사용한 시점부터 5시간 동안 쓸 수 있는 양. 시간이 지나면 다시 채워집니다.
  • 주간 한도weekly limit: 계정마다 정해진 요일·시각에 초기화됩니다. 모든 모델에 걸리는 한도이며, Fable에는 별도 막대가 있습니다.
  • 사용 크레딧usage credits: 한도에 닿은 뒤에도 일을 계속하기 위해 켜는 종량제 옵션입니다. 클로드 코드에서 /usage-credits로 설정 페이지를 엽니다. 월 지출 한도를 걸 수 있습니다.

사용량을 더 빨리 쓰게 만드는 요인(도움말 센터 기준): 메시지 길이, 첨부 파일 크기, 현재 대화 길이, 도구 사용(웹 검색·리서치), 모델 선택, 노력 수준, 아티팩트, 코드 실행·파일 생성·브라우징 같은 다단계 작업. 사실

모델별 차감 비율은 비공개입니다. 구독 한도에서 Opus와 Sonnet이 각각 얼마나 차감되는지는 공식 수치가 없습니다. 이 사이트에서 "Opus가 Sonnet보다 한도를 더 쓴다"고 말할 때는 API 단가(Opus 5.5가 Sonnet 5.5의 2배)를 근거로 한 추론입니다. 다만 Opus 5.5는 같은 일을 더 적은 토큰으로 끝내는 경향이 있다고 문서에 적혀 있으므로, 실제 차이는 작업마다 다릅니다. /usage의 내역으로 직접 확인하세요.

Pro 운용 전략 추론

  1. 1
    한 세션 = 한 작업작업이 끝나면 /clear. 긴 세션은 매 요청마다 전체 대화를 다시 보내므로 한도가 빨리 닳습니다(공식 문서의 "긴 세션에서 사용량이 오르는 이유").
  2. 2
    계획은 한 번, 구현은 가볍게큰 기능은 계획 모드에서 방향을 확정한 뒤 구현합니다. 잘못된 방향으로 구현했다가 되돌리는 것이 가장 비쌉니다. opusplan(계획은 Opus, 실행은 Sonnet)이 이 흐름을 자동화합니다.
  3. 3
    노력 수준은 기본(medium) 유지막혔을 때만 /effort high나 프롬프트에 ultrathink를 붙여 한 턴만 깊게 생각시킵니다.
  4. 4
    Fable은 꼭 필요할 때만Pro에서 Fable은 사용 크레딧으로 청구됩니다. 클로드 코드는 크레딧이 청구되기 전에 동의를 묻습니다. 단, claude -p 비대화 모드에서는 묻지 않고 청구하므로 스크립트에서 Fable을 지정하지 않도록 주의합니다. 사실
  5. 5
    한도 시각에 맞춰 일 배치5시간 창이 리셋되기 직전에는 작은 일, 리셋 직후에는 큰 리팩터링처럼 배치하면 중단이 줄어듭니다.
  6. 6
    채팅(claude.ai)과 코드의 역할 분리둘이 같은 한도를 씁니다. 개념 질문은 짧게 채팅에서, 파일을 만지는 일은 클로드 코드에서 하면 불필요한 파일 읽기를 줄일 수 있습니다.

Max 운용 전략 추론

  1. 1
    병렬 세션claude --worktree나 데스크톱 앱의 병렬 세션으로 기능 A·B·버그 수정을 동시에 진행합니다. 워크트리(worktree)는 같은 저장소를 폴더별로 분리해 서로의 수정이 충돌하지 않게 합니다.
  2. 2
    백그라운드 위임claude agents(에이전트 뷰)에서 여러 세션을 띄워 두고, 사람의 입력이 필요한 세션만 확인합니다. /background로 현재 세션을 백그라운드로 보낼 수 있습니다.
  3. 3
    Fable 5.1로 장시간 자율 작업근본 원인 조사, 큰 마이그레이션, 아키텍처 결정처럼 한 번에 앉아서 끝나지 않는 일에 씁니다. 결과 조건을 /goal로 걸어 두면 조건을 만족할 때까지 계속 작업합니다.
  4. 4
    독립 검증에 투자구현 세션과 리뷰 세션을 나눕니다(작성자/검토자 패턴). /code-review, /security-review를 습관화합니다.
  5. 5
    루틴으로 무인 작업매일 아침 PR 요약, 의존성 점검 같은 반복 작업을 클라우드 루틴(/schedule)으로 돌립니다. 루틴은 하루 실행 횟수 상한이 따로 있습니다. 사실
  6. 6
    그래도 컨텍스트 위생은 똑같이한도가 커져도 컨텍스트가 길어질수록 품질이 떨어지는 것은 같습니다. 공식 문서가 강조하는 첫 번째 제약입니다. 사실

언제 Max로 올릴까 추론

  • 일주일에 여러 번 5시간 한도 때문에 작업이 끊기고, 이미 /clear·모델 선택 같은 절약 습관을 지키고 있을 때.
  • 여러 세션을 동시에 돌리거나 Fable로 긴 작업을 맡기고 싶을 때.
  • 반대로, 한도에 가끔만 닿는다면 Pro + 필요 시 사용 크레딧이 더 경제적일 수 있습니다. /usage의 지난 7일 내역(w 키)을 보고 판단하세요.

결론

  • Claude 탭은 일반 업무용입니다. 질문, 리서치, 문서·스프레드시트·발표 자료 만들기, 연결한 앱(Gmail, Google Drive 등)의 자료로 일하기, 정기 예약 작업을 맡깁니다. 사실
  • Code 탭은 클로드 코드입니다. 내가 고른 프로젝트 폴더의 코드를 읽고, 고치고, 실행하고, diff로 검토하고, git·PR까지 다룹니다. 사실

Claude 탭의 현재 제한 사실

  • GitHub 연동("Add from GitHub")을 지원하지 않습니다. 저장소 작업은 Code 탭에서 합니다.
  • 대화 분기(branching)를 쓸 수 없습니다.
  • 시크릿 채팅(incognito)은 통합 이전 방식으로 동작합니다.
  • 검색에 예전 Cowork 작업은 포함되지 않습니다.
  • Dispatch는 신규 사용자에게 제공되지 않습니다.

위 제한은 통합 안내 도움말 문서 기준이며, 배포가 진행되면서 바뀔 수 있습니다.

노력 수준(effort)이란

노력 수준effort은 모델이 답하기 전에 얼마나 생각할지를 정하는 다이얼입니다. 최신 모델은 적응형 추론adaptive reasoning을 써서, 같은 노력 수준 안에서도 쉬운 단계는 짧게, 어려운 단계는 길게 생각합니다. 생각에 쓰인 토큰도 출력 토큰으로 계산됩니다. 클로드 코드에서는 Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable의 생각 기능을 끌 수 없고 노력 수준으로만 조절합니다. 레시피 F: Haiku 5.5 1차 분류 → 필요할 때만 Sonnet 5.5로 넘기기 예시 (Python, anthropic SDK)
import anthropic

client = anthropic.Anthropic()  # ANTHROPIC_API_KEY 환경 변수 사용

def text_of(response) -> str:
    # Haiku 5.5는 응답이 thinking 블록으로 시작할 수 있으므로 type으로 골라냄
    return "".join(b.text for b in response.content if b.type == "text").strip()

def route(ticket: str) -> str:
    triage = client.messages.create(
        model="claude-haiku-5-5",
        max_tokens=2048,                       # 생각 토큰도 포함되므로 여유 있게
        output_config={"effort": "low"},
        system="문의를 SIMPLE 또는 COMPLEX 중 하나로만 분류해. 다른 말은 쓰지 마.",
        messages=[{"role": "user", "content": ticket}],
    )
    if triage.stop_reason == "refusal":       # Haiku 5.5는 안전 분류기 거절이 새로 생김
        return "거절됨: 사람 검토 필요"
    label = text_of(triage)
    model = "claude-haiku-5-5" if label == "SIMPLE" else "claude-sonnet-5-5"
    answer = client.messages.create(
        model=model,
        max_tokens=8192,
        output_config={"effort": "medium"},
        messages=[{"role": "user", "content": ticket}],
    )
    return text_of(answer)

output_config.effort, stop_reason: "refusal", 응답 블록을 type으로 고르는 방식은 공식 문서 기준입니다. temperature 같은 샘플링 매개변수를 넣으면 Haiku 5.5에서 400 오류가 나므로 빼 두었습니다. 운영에서는 네트워크 오류 재시도(SDK 기본 재시도 포함), 분류 결과가 두 값 중 하나가 아닐 때의 처리, 비용 로깅을 추가하세요. 사실 + 추론

  1. 네, 쓸 수 있고 공식적으로 권장되는 용도입니다. 서브에이전트 정의 파일에 model: haiku를 쓰면 됩니다. 사실

모델이 정해지는 순서 사실

  1. 호출할 때 지정한 model 값 (클로드가 서브에이전트를 부르며 지정)
  2. 정의 파일의 model 항목 (inherit는 메인 대화 모델을 따름)
  3. 환경 변수 CLAUDE_CODE_SUBAGENT_MODEL (별칭 또는 모델 ID)
  4. 메인 대화의 모델

3번은 1·2번보다 약합니다. 정의 파일·호출 지정까지 무시하고 전부 한 모델로 돌리려면 CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1을 함께 설정합니다(v2.1.257 이상). 단, CLAUDE_CODE_SUBAGENT_MODEL만으로는 내장 Explore·Plan 서브에이전트의 모델이 바뀌지 않습니다. 이 변수는 에이전트 팀 팀원과 동적 워크플로 작업자의 기본 모델로도 쓰입니다. 사실

클로드 코드 기본기

설치부터 첫 세션, 꼭 알아야 할 조작

클로드 코드는 에이전트형 코딩 도구agentic coding tool입니다. 질문에 답만 하는 채팅과 달리, 파일을 읽고, 명령을 실행하고, 코드를 고치고, 결과를 확인하는 과정을 스스로 반복합니다. 이 반복을 에이전트 루프agentic loop라고 부릅니다.

이 페이지는 터미널 기준입니다. 데스크톱 앱 Code 탭에서는 설치 없이 바로 쓰며, 세션·권한 모드·단축키 조작이 다릅니다. → Claude 탭과 Code 탭의 "Code 탭 사용법"

macOS · Linux · WSL (권장 방식, 자동 업데이트)

Windows PowerShell

  • 설치 후 새 터미널에서 claude --version. "찾을 수 없음"이 뜨면 PATH 문제입니다.

- 테스트(단일 파일): npx vitest run path/to/file.test.ts
- 타입 검사: npm run typecheck   # 변경을 마치면 반드시 실행
- 린트: npm run lint

# 코드 스타일
- ES 모듈(import/export)만 사용, CommonJS 금지
- API 응답 형식은 src/lib/response.ts의 ok()/fail()을 사용

Code 탭 기본기

클로드 코드는 에이전트형 코딩 도구agentic coding tool입니다. 질문에 답만 하는 채팅과 달리, 파일을 읽고, 명령을 실행하고, 코드를 고치고, 결과를 확인하는 과정을 스스로 반복합니다. 데스크톱 앱의 Code 탭은 이 클로드 코드를 버튼과 패널로 쓰는 화면입니다.

세션 시작 사실

변경 검토: diff 창과 Review code 사실

  • 클로드가 파일을 고치면 +12 -1 같은 표시가 생기고, 누르면 왼쪽 파일 목록·오른쪽 변경 내용의 diff 창이 열립니다.
  • diff의 줄을 클릭해 댓글을 달고 Ctrl+Enter로 한꺼번에 보내면 클로드가 반영해 새 diff를 만듭니다.
  • Review code: 커밋 전에 컴파일 오류, 확실한 논리 오류, 보안 취약점, 명백한 버그를 검토해 diff에 댓글로 남깁니다. 스타일·포맷·기존 문제·린터가 잡을 것은 지적하지 않습니다.
  • PR을 열면 CI 상태 표시줄이 생기고, Auto-fix(실패한 CI 자동 수정)와 Auto-merge(통과 시 squash 병합) 토글이 있습니다. GitHub CLI(gh)가 설치·로그인돼 있어야 합니다. → CLI 도구

앱 미리보기: Browser 창 사실

  • 클로드가 개발 서버를 띄워 Browser 창에서 열고, 스크린샷·DOM 확인·클릭·폼 입력으로 자기 변경을 검증합니다. 기본으로 편집 후 자동 검증(autoVerify)이 켜져 있습니다.
  • 서버 시작 명령이 특수하면 .claude/launch.json을 고칩니다. 자동 검증을 끄려면 같은 파일에 "autoVerify": false.
  • 외부 사이트 조작은 사이트마다 처음에 승인(Allow once / Always allow / Deny)을 묻습니다. 결제, 계정 생성, CAPTCHA 우회는 하지 않습니다.

그 밖의 Code 탭 기능 사실

  • 내장 터미널 (Ctrl+`): 세션의 작업 폴더에서 열리고 클로드와 같은 환경을 씁니다. 내가 직접 git, gh 등을 칠 때 사용.
  • 환경 변수: Windows 앱은 사용자·시스템 환경 변수를 물려받지만 PowerShell 프로필은 읽지 않습니다. 환경 드롭다운 → Local에 마우스 → 톱니바퀴(로컬 환경 편집기)에서 설정하면 모든 로컬 세션과 미리보기 서버에 적용됩니다.
  • 세션 간 메시지: "인증 리팩터링을 한 세션이 어디야?", "API 세션의 결론은?"처럼 물으면 다른 Code 탭 세션을 읽고 메시지를 보냅니다.
  • 작업 칩: 범위 밖의 고칠 거리를 발견하면 칩으로 제안하고, 누르면 새 세션(자체 워크트리)에서 시작합니다.
  • Dispatch: 다른 화면에서 맡긴 개발 작업을 Code 세션으로 만들어 주는 기능. 채팅과 Cowork가 합쳐진 Claude 화면에서는 신규 사용자에게 제공되지 않는다고 도움말 센터가 밝히고 있습니다. → Claude 탭과 Code 탭
  • Computer use (연구 미리보기, Pro·Max, macOS·Windows): Settings > General에서 켜면 데스크톱 앱을 직접 조작. 실제 화면에서 동작하므로 승인 범위에 주의.
  • 터미널 세션 가져오기: 터미널에서 /desktop을 치면 그 세션이 데스크톱 앱으로 넘어옵니다.

출력 걸러내기 훅 예시

공식 문서의 테스트 출력 필터 패턴을 단순화한 버전입니다. 테스트 명령이면 실패 부분만 남기도록 명령을 바꿉니다. jq가 필요합니다.

~/.claude/hooks/filter-tests.sh
#!/usr/bin/env bash
# PreToolUse 훅: 테스트 명령이면 실패 관련 줄만 남기도록 명령을 다시 씀
set -euo pipefail
input="$(cat)"
cmd="$(printf '%s' "$input" | jq -r '.tool_input.command // empty')"

case "$cmd" in
  "npm test"*|"pytest"*|"go test"*)
    new="$cmd 2>&1 | grep -E -A 5 '(FAIL|ERROR|error:)' | head -100"
    printf '%s' "$input" | jq --arg c "$new" '{
      hookSpecificOutput: {
        hookEventName: "PreToolUse",
        permissionDecision: "allow",
        updatedInput: (.tool_input + {command: $c})
      }}'
    ;;
  *) echo '{}' ;;
esac
settings.json 에 등록
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "~/.claude/hooks/filter-tests.sh" }] }
    ]
  }
}
트레이드오프. 이 훅은 실패 줄만 남기므로, 실패 원인이 앞쪽 경고에 있으면 클로드가 놓칠 수 있습니다. 또 permissionDecision: "allow"는 해당 명령의 권한 확인을 건너뛰게 하므로, 신뢰하는 테스트 명령에만 적용하세요. chmod +x로 실행 권한을 주고 /hooks에서 등록을 확인합니다. 추론

MCP로 외부 도구 연결하기

MCPModel Context Protocol는 AI가 외부 도구·데이터에 연결하는 오픈 표준입니다. 이슈 트래커, 데이터베이스, 디자인 도구, 모니터링 같은 서비스의 내용을 복사해 붙여넣고 있다면 MCP 서버를 연결할 때입니다.

  • 원격 서비스는 claude mcp add --transport http 이름 URL, 내 컴퓨터에서 도는 도구는 claude mcp add 이름 -- 실행명령. 사실
  • 신뢰하는 서버만 연결합니다. 외부 콘텐츠를 가져오는 서버는 프롬프트 인젝션prompt injection 위험이 있습니다. 사실
  • 같은 일을 CLI로 할 수 있으면 CLI가 컨텍스트 효율이 더 좋습니다. 사실

추가하는 법 사실

원격 HTTP 서버 (권장 전송 방식)
claude mcp add --transport http notion https://mcp.notion.com/mcp

로컬 stdio 서버: -- 뒤가 실제 실행 명령

--(대시 두 개)는 클로드 코드의 옵션과 서버 실행 명령을 나눕니다. 이것이 없으면 서버의 --port 같은 플래그를 클로드 코드가 자기 옵션으로 해석합니다. SSE 방식은 더 이상 권장되지 않으며, HTTP로 추가하면 필요할 때 자동으로 SSE로 전환됩니다(v2.1.265 이상).

다른 앱용 JSON 설정을 그대로 쓰기
claude mcp add-json example '{"command":"npx","args":["-y","@example/mcp-server"]}'
claude mcp add-from-claude-desktop   # Claude Desktop 설정 가져오기 (macOS·WSL)

url이 있는 JSON 항목에는 반드시 "type": "http"를 넣어야 합니다. 없으면 stdio 서버로 오인되어 건너뜁니다.

CLI 도구 활용

CLI 도구command-line interface tool는 터미널에서 명령으로 쓰는 프로그램입니다(git, gh, wrangler, npm 등). 터미널에서 쓰든 Code 탭에서 쓰든 클로드는 내부에서 이 명령들을 실행하며 일합니다. 여러분은 명령을 직접 치는 대신 "PR을 만들어 줘"라고 요청하고, 클로드가 gh pr create를 실행하는 식입니다.

결론

  1. 외부 서비스에 공식 CLI가 있으면 MCP보다 CLI가 컨텍스트 효율이 좋습니다. 공식 문서는 GitHub를 쓰면 gh 설치를 권합니다. 사실
  2. 설치와 로그인은 내가 먼저 해 둡니다(내 터미널, Code 탭이면 내장 터미널 Ctrl+`). 클로드는 이미 로그인된 CLI를 사용합니다. 추론
  3. 무엇을 묻지 않고 실행해도 되는지는 권한 규칙(settings.json)으로 정합니다. 터미널에서는 /permissions 화면을 쓸 수 있고, Code 탭에는 이 화면이 없으므로 파일을 직접 편집합니다. 사실
  4. 운영 배포·원격 DB 변경처럼 되돌리기 어려운 명령은 ask 규칙으로 항상 확인받습니다. 추론

클로드는 CLI를 어떻게 실행하나 사실

클로드 코드는 Bash 도구(Windows에서는 PowerShell 도구도)로 명령을 실행합니다. 알아 두면 결과를 이해하기 쉬운 동작:

항목동작
프로세스명령마다 별도 프로세스로 실행
작업 폴더프로젝트(또는 추가한 폴더) 안에서 cd하면 다음 명령에도 유지. 밖으로 나가면 프로젝트 폴더로 되돌아감
환경 변수export는 다음 명령에 유지되지 않음. 셸 시작 파일(~/.bashrc 등)의 별칭·함수는 적용됨. 변수를 고정하려면 클로드 코드를 실행하기 전에 CLAUDE_ENV_FILE을 지정하거나 SessionStart 훅 사용. 가상 환경(venv·conda)은 클로드 코드 실행 전에 활성화
시간 제한기본 2분, 최대 10분(BASH_DEFAULT_TIMEOUT_MS, BASH_MAX_TIMEOUT_MS로 조정). 시간을 넘기면 멈추지 않고 백그라운드로 옮겨 계속 실행(sleep으로 시작하는 명령 제외)
긴 실행개발 서버·감시 빌드는 백그라운드 작업으로 실행. 터미널에서는 /tasks로 목록 확인·중지
출력 길이성공한 명령은 약 3만 자까지 바로 전달, 넘으면 파일로 저장되고 앞부분(최대 2,000자) 미리보기와 경로만 전달(클로드가 필요할 때 파일을 읽음). 실패한 명령은 약 1만 자까지, 넘으면 앞뒤 일부만 전달
종료 코드 1grep, rg, find, diff, git diff, git grep 등은 "결과 없음/차이 있음"으로 정상 처리. 그 밖의 명령은 실패로 처리
로그 감시Monitor 도구로 명령 출력을 줄 단위로 받아 반응. 기본 5분, 최대 30분 동안 감시

권한 규칙: 무엇을 묻지 않고 실행할까

권한 규칙은 모델이 아니라 클로드 코드가 강제합니다. 터미널에서는 /permissions로 규칙을 보고 추가할 수 있고, Code 탭에는 이 화면이 없으므로 설정 파일을 편집합니다(클로드에게 편집을 요청해도 되지만 .claude 폴더는 보호 경로라 승인을 묻습니다). 사실

파일범위
~/.claude/settings.json내 모든 프로젝트
.claude/settings.json이 프로젝트, 팀과 공유 (git 커밋)
.claude/settings.local.json이 프로젝트, 나만

규칙 문법 사실

  • 세 종류: allow(묻지 않고 실행), ask(항상 확인), deny(금지). 평가 순서는 deny → ask → allow이며, 더 구체적인 allow가 있어도 넓은 deny가 이깁니다.
  • 어느 범위에서든 deny가 있으면 다른 범위의 allow로 풀 수 없습니다.
  • *는 공백 포함 아무 글자나 대신합니다. *는 하위 명령 뒤에 둡니다: Bash(git log *)는 git log만, Bash(git *)는 모든 git 명령.
  • 끝의 " *"(공백+별표)는 명령만 단독으로 쓴 경우도 포함: Bash(ls *)는 ls와 ls -la에 맞고 lsof에는 안 맞음.
  • &&, ||, ;, |로 이은 명령은 각 부분이 따로 규칙에 맞아야 허용됩니다.
  • timeout, nice, nohup 같은 래퍼는 벗기고 비교하지만, npx, docker exec 같은 실행기는 벗기지 않습니다. Bash(npx *)는 npx로 실행하는 모든 것을 허용하므로 쓰지 말고, Bash(npx wrangler tail *)처럼 구체적으로 씁니다.
  • ls, cat, grep, find, 읽기 전용 git 같은 읽기 전용 명령은 규칙 없이도 묻지 않습니다.
  • Windows PowerShell 도구에는 PowerShell(...) 규칙이 따로 있습니다.
.claude/settings.json — GitHub + Cloudflare 프로젝트 예시
{
  "permissions": {
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm run typecheck)",
      "Bash(npx vitest run *)",
      "Bash(gh issue view *)",
      "Bash(gh pr view *)",
      "Bash(gh pr diff *)",
      "Bash(gh pr checks *)",
      "Bash(gh run view *)",
      "Bash(npx wrangler whoami)",
      "Bash(npx wrangler deploy --dry-run *)",
      "Bash(npx wrangler d1 migrations list *)"
    ],
    "ask": [
      "Bash(git push *)",
      "Bash(gh pr merge *)",
      "Bash(npx wrangler deploy)",
      "Bash(npx wrangler rollback *)",
      "Bash(npx wrangler d1 execute *)",
      "Bash(npx wrangler d1 migrations apply *)"
    ],
    "deny": [
      "Bash(npx wrangler secret *)",
      "Read(./.env)",
      "Read(./.dev.vars)"
    ]
  }
}

이 예시의 판단 근거 추론:

  • deploy --dry-run은 allow, 플래그 없는 deploy는 정확히 일치하는 ask 규칙. ask를 Bash(npx wrangler deploy *)로 넓히면 평가 순서(deny → ask → allow) 때문에 dry-run까지 물어보게 되므로 일부러 좁혔습니다. 대신 --env production처럼 플래그가 붙은 배포는 이 규칙에 걸리지 않고 권한 모드의 기본 동작을 따릅니다(Manual은 물어봄, Auto는 분류기가 운영 배포를 기본 차단). 플래그 붙은 배포도 항상 묻게 하려면 Bash(npx wrangler deploy --env *)처럼 쓰는 형태별로 ask 규칙을 추가합니다.
  • D1 execute와 migrations apply는 local·remote를 규칙 문법으로 안정적으로 구분하기 어려워(플래그 위치가 바뀌면 불일치) 통째로 ask에 둡니다.
  • secret은 값이 대화에 남지 않도록 deny하고 직접 실행합니다. .env·.dev.vars 읽기를 막는 것은 비밀값 노출 방지용입니다(Cloudflare 문서: 로컬 개발용 비밀값은 Wrangler 설정 파일과 같은 폴더의 .dev.vars 또는 .env 중 하나에 두고, 둘 다 git에 커밋하지 말 것. 사실)
규칙은 보안 경계가 아닙니다. 공식 문서에 따르면 Bash 규칙은 클로드가 쓴 명령 "글자"와 비교합니다. Bash(git push *)는 git -C . push나 sh -c '...' 형태를 잡지 못합니다. 확실히 막아야 하는 것은 샌드박스나 PreToolUse 훅을 함께 쓰라고 안내합니다. 또 Auto 모드에서는 Bash(*)처럼 넓은 allow 규칙을 무시하고 분류기가 검토하며, 분류기는 운영 배포·마이그레이션을 기본으로 막습니다. 사실

동적 주입 dynamic context injection

줄 맨 앞(또는 공백 뒤)에 !`명령`을 쓰면, 스킬이 클로드에게 전달되기 전에 명령을 실행하고 그 출력으로 바꿔 넣습니다. 여러 줄은 ```! 코드 블록. 명령이 실패하면 스킬 호출 전체가 중단되며, 권한 규칙 검사를 통과해야 실행됩니다(Auto 모드가 아니면 묻지 않고 거부됨 → allowed-tools로 미리 허용). 실행 셸은 Windows에서 Git Bash가 없으면 PowerShell입니다. 사실

실전 예시 1: GitHub 이슈 처리 (부작용 있음, 내가 부를 때만) 예시

gh가 설치·로그인돼 있다고 가정합니다(→ CLI 도구 활용). 부를 때는 /fix-issue 123.

.claude/skills/fix-issue/SKILL.md 예시
---
name: fix-issue
description: GitHub 이슈 번호를 받아 재현 테스트부터 PR까지 처리한다. 사용자가 이슈 수정을 요청할 때 사용.
disable-model-invocation: true
argument-hint: [issue-number]
allowed-tools: Bash(gh issue view *) Bash(npm test *)
---
GitHub 이슈 $ARGUMENTS 를 해결한다.

1. `gh issue view $ARGUMENTS` 로 내용 확인
2. 원인 파일을 찾고, 재현하는 실패 테스트를 먼저 작성
3. 수정 후 `npm test`, `npm run typecheck` 통과 확인
4. 변경 요약과 실행한 명령·결과를 보고하고 커밋 메시지 제안

설계 이유 추론: 커밋·PR로 이어지는 절차라 disable-model-invocation: true로 내가 부를 때만 실행되게 했고, allowed-tools에는 읽기 성격의 gh issue view와 테스트 명령만 넣었습니다. 실패 테스트를 먼저 쓰게 한 것은 클로드가 스스로 수정 결과를 검증할 수단을 만들기 위해서입니다(→ 코딩 특별 페이지).

실전 예시 2: D1 마이그레이션 절차 (부작용 있음, 내가 부를 때만) 예시

Cloudflare D1을 쓰는 프로젝트를 가정한 예시입니다. 가정 데이터베이스 이름 app-db, 테스트 명령 npm test.

.claude/skills/d1-migrate/SKILL.md
---
name: d1-migrate
description: D1 스키마 변경을 새 마이그레이션 파일로 만들고 로컬에서 검증한다. 원격 적용은 사용자 확인 후에만. 스키마 변경, 테이블·컬럼 추가 요청 시 사용.
disable-model-invocation: true
argument-hint: [변경 내용 요약]
allowed-tools: Bash(npx wrangler d1 migrations create *) Bash(npx wrangler d1 migrations list *) Bash(npm test *)
---
## 현재 미적용 마이그레이션 (로컬)
!`npx wrangler d1 migrations list app-db --local`

## 할 일: $ARGUMENTS

1. 기존 migrations/ 파일은 절대 수정하지 않는다. 새 파일만 만든다:
   `npx wrangler d1 migrations create app-db <짧은-설명>`
2. 생성된 SQL 파일에 변경을 작성한다. 기존 데이터가 있는 테이블의 NOT NULL 컬럼 추가는
   기본값을 주거나 단계를 나눈다.
3. 로컬 적용 명령 `npx wrangler d1 migrations apply app-db --local` 을 실행한다.
   확인 질문 때문에 진행되지 않으면 멈추고, 사용자에게 터미널에서 직접 실행해 달라고 요청한다.
4. `npm test` 로 회귀 확인.
5. 보고: 생성 파일 경로, SQL 전문, 테스트 결과, 그리고
   원격 적용 명령 `npx wrangler d1 migrations apply app-db --remote` 를 **실행하지 말고**
   제시만 한다. 원격 적용 여부는 사용자가 결정한다.

설계 이유 추론: 원격 DB 변경은 되돌리기 어려우므로 스킬이 실행하지 않고 제시만 하게 했고, allowed-tools에는 위험도 낮은 명령만 넣었습니다. migrations apply는 CLI 페이지의 권한 규칙 예시에서 ask로 두었으므로 실행 시 항상 묻습니다. 위의 !`...` 줄은 스킬을 부를 때마다 실행되는데, migrations list가 allowed-tools에 있어 묻지 않고 실행됩니다. 주의할 점: 주입 명령이 실패하면 스킬 호출 전체가 중단되므로(사실), 로컬 D1 상태가 아직 없어 list가 오류를 내는 프로젝트라면 이 줄을 빼세요. Cloudflare 문서에 따르면 migrations apply는 적용 전에 확인을 묻고(CI 환경에서는 생략) 적용 후 백업을 남깁니다. 사실 이 확인 질문을 클로드의 셸이 어떻게 처리하는지는 확인하지 못해 3단계에 대비책을 넣었습니다 확인 필요.

훅 hooks

훅은 클로드 코드 수명 주기의 정해진 시점에 자동으로 실행되는 셸 명령입니다. CLAUDE.md의 지시는 "권고"지만 훅은 "보장"입니다. 훅은 내 계정 권한으로 임의 명령을 실행하므로, 남이 만든 훅은 내용을 읽고 쓰세요. 사실

주요 이벤트언제
SessionStart세션 시작·재개, 압축 직후(compact 매처)

#!/usr/bin/env bash
# PreToolUse(Edit|Write): 보호 대상 경로면 종료 코드 2로 차단
input="$(cat)"
path="$(printf '%s' "$input" | jq -r '.tool_input.file_path // empty')"
path="${path//\\//}"   # Windows 역슬래시 정규화

for p in ".env" "package-lock.json" ".git/" "migrations/"; do
  if [[ "$path" == *"$p"* ]]; then
    echo "차단됨: $path 는 보호 대상($p)입니다. 새 파일을 만들거나 사람에게 요청하세요." >&2
    exit 2
  fi
done
exit 0

한계. 이 훅은 편집 도구만 막습니다. 클로드가 Bash로 파일을 바꾸면 통과합니다. 빈틈 없이 막으려면 권한 거부 규칙(permissions.deny)이나 샌드박스를 함께 씁니다. 훅의 if 필터도 "최선의 노력" 수준이라 강제 수단으로는 권한 시스템을 쓰라고 문서가 안내합니다. 사실

판단이 필요한 검사는 "type": "prompt"(모델이 한 번 판단) 또는 "type": "agent"(실험적, 파일을 읽고 명령을 실행해 검증)를 쓸 수 있습니다. 예를 들어 Stop 훅에서 "모든 테스트가 통과했는지" 확인해 미완이면 계속 일하게 할 수 있습니다. Stop 훅이 연속 8번 막으면 클로드 코드가 강제로 멈추므로, 입력의 stop_hook_active를 확인해 무한 반복을 피합니다. 사실

Mod: 클로드 코드의 화면과 동작을 내 코드로 바꾸기

Modmod는 클로드 코드 안에서 직접 실행되는 JavaScript·TypeScript 함수 묶음입니다. 게임의 "모드"처럼, 클로드 코드에 내 패널을 붙이고, 스피너 문구를 바꾸고, 위험한 명령을 붙잡고, 나만의 /명령을 추가합니다.

결론

  1. Mod는 플러그인의 한 종류입니다. 플러그인 안의 hooks/hooks.json에 "modules": ["./register.js"]가 있으면 Mod가 됩니다. 사실
  2. 기존 훅(설정 훅)이 "바깥에서 셸 명령을 실행"한다면, Mod는 "클로드 코드 안에서 함수로 실행"되어 화면을 그리고, 도구 호출·프롬프트·요청을 보거나 바꾸거나 대신 처리할 수 있습니다. 사실
  3. 필요 버전: 터미널 v2.1.287 이상, 데스크톱 앱 내장판 v2.1.286 이상. 기본으로 켜져 있습니다. 화면을 그리는 것은 터미널과 데스크톱 앱 Code 탭뿐입니다. 사실
  4. 가장 쉬운 시작은 클로드에게 "~하는 mod 만들어 줘"라고 말하기입니다. 내장 plugin-authoring 스킬로 클로드가 작성하고, 승인하면 그 세션에서 바로 핫 리로드됩니다. 사실
  5. Mod는 샌드박스 없이 내 권한으로 실행되는 코드입니다. 파일·비밀값·네트워크에 접근하고 도구 호출을 대신 승인할 수도 있습니다. 믿을 수 있는 출처만 설치하고, 설치 전 claude plugin validate로 무엇을 하는지 확인하세요. 사실

쉽게 이해하기

직관적 설명 (비유): 클로드 코드를 "식당 주방"이라고 하면, 설정 훅은 주방 밖에 붙인 "주문 들어오면 벨 울리기" 장치이고, 스킬은 요리사에게 건네는 레시피 카드입니다. Mod는 주방 안에 들어와 일하는 내 직원입니다. 주문서(프롬프트)를 고쳐 쓰고, 위험한 조리(명령)를 멈춰 세우고, 주방 벽에 내 현황판(패널)을 붙일 수 있습니다.

실제 구조 사실: 클로드 코드는 도구 호출, 프롬프트 제출, 모델 요청, 화면 그리기 같은 순간마다 이벤트event를 발생시킵니다. Mod는 register(on) 함수 안에서 on('이벤트이름', 함수)로 처리기(문서에서 "hook")를 등록합니다. 처리기들은 미들웨어 사슬처럼 이어지고, 맨 끝이 클로드 코드 자신의 동작입니다. 각 처리기는 세 인자 $(Mods API), e(이벤트 데이터, 읽기 전용), next(다음 처리기 호출)를 받습니다.

처리기가 하는 일코드 모양예
관찰 (보고 그대로 보냄)return next(e)도구 호출 횟수 세기

대답 (직접 처리, 뒤는 실행 안 함)return { deny: '이유' }강제 푸시 차단

// 아래 처리기들이 함께 쓰는 개수
let calls = 0

// Mod가 로드될 때 클로드 코드가 한 번 호출
export function register(on) {
  // 세션 시작 때(첫 프롬프트 전), 그리고 리로드될 때마다 실행
  on('session.start', async ($, e, next) => {
    // /tally 명령 추가
    await $.command.register({
      name: 'tally',
      description: 'Show how many tool calls Claude has made',
    })
    return next(e)
  })

  // 클로드가 도구를 쓰기 직전마다 실행
  on('tool.call', async ($, e, next) => {
    calls += 1
    $.ui.invalidate('ui.render')   // 화면을 다시 그려 새 숫자 표시
    return next(e)                 // 도구는 평소대로 실행
  })

  // /tally 입력 때만 실행 (두 번째 인자 = 매처)
  on('command.run', { command: 'tally' }, async () => {
    return { text: 'Claude has made ' + calls + ' tool calls since this mod loaded' }
  })

  // 스피너를 그릴 때마다 실행: 기존 스피너 유지 + 뒤에 문구 추가
  on('ui.render', { component: 'Spinner' }, async ($, e, next) => {
    return next({ ...e, props: { ...e.props, suffix: ' · tool calls: ' + calls + '…' } })
  })
}

예시 1. 위험한 명령은 나에게 먼저 묻기 사실 (공식 예제)

hooks/register.js
const RISKY = /\brm\s+-rf?\b|\bgit\s+reset\s+--hard\b|\bgit\s+push\b.*--force/

export function register(on) {
  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    if (!RISKY.test(e.command)) return next(e)      // 나머지 명령은 그대로
    let answer = 'Refuse'                            // 아무도 답하지 않으면 거절
    try {
      answer = await $.ui.ask('Run this command? ' + e.command, ['Run it', 'Refuse'])
    } catch {
      // 사용자가 닫았거나 claude -p 실행이라 물을 사람이 없음
    }
    if (answer !== 'Run it') {
      return { deny: 'The user declined this command. Ask before trying a different approach.' }
    }
    return next(e)                                   // 승인 후에도 일반 권한 확인은 그대로 진행
  })
}

정규식은 git push -f 같은 다른 표기는 놓칩니다. 기다리는 시간은 $.ui.ask 같은 API 호출 안에서 보내야 처리기 시간 제한(10초)에 걸리지 않습니다. 시간 초과로 처리기가 건너뛰어지면 붙잡았던 명령이 실행되므로, 차단용 처리기에는 .catch()로 "실패하면 거절"을 붙이는 것이 안전합니다. 사실

핵심 흐름: 명령 등록 → 패널 열기 → ui.render에서 트리 반환
const PANE = 'hello-tabs'
let tab = 'one'
let count = 0

export function register(on) {
  on('session.start', async ($, e, next) => {
    await $.command.register({ name: 'hello-tabs', description: 'Open the hello-tabs pane' })
    const saved = await $.store.get('count')        // 이전 세션 값 불러오기
    if (typeof saved === 'number') count = saved
    return next(e)
  })

  on('command.run', { command: 'hello-tabs' }, async ($) => {
    await $.ui.open({ id: PANE, title: 'Hello tabs', focus: true, closeOnEscape: true })
    return {}                                        // 대화창에는 아무것도 출력 안 함
  })

  on('ui.render', { component: 'Pane' }, async ($, e, next) => {
    if (e.requestId !== PANE) return next(e)         // 다른 Mod의 패널은 건드리지 않음
    const { Box, Text, Button } = $.ui.resolve(e)
    const redraw = () => $.ui.invalidate('ui.render')
    const tabButton = (name, label, hotkey) =>
      Button({ key: 'tab-' + name, label, hotkey, plain: true, dimColor: tab !== name,
               onPress: () => { tab = name; redraw() } })
    const body = tab === 'one'
      ? [Text({ children: ['This is the first tab.'] })]
      : [Box({ flexDirection: 'row', columnGap: 2, children: [
          Button({ key: 'more', label: 'Add one', hotkey: 'a',
                   onPress: async () => { count += 1; redraw(); await $.store.set('count', count) } }),
          Text({ children: ['Count: ' + count] }),
        ] })]
    return Box({ flexDirection: 'column', children: [
      Box({ flexDirection: 'row', columnGap: 3, children: [tabButton('one', 'One', '1'), tabButton('two', 'Two', '2')] }),
      Text({ children: [' '] }),
      ...body,
    ] })
  })
}

패널 키: Tab 다음 컨트롤, Enter 누르기, 버튼 핫키, Ctrl+X 후 화살표로 크기 조절, Ctrl+X 후 X로 닫기, Esc로 입력창에 포커스 돌려주기. 사실

결론

  1. 무엇: 프로젝트 대화 1개(코디네이터) + 스레드 여러 개(작업자) + 공유 메모리·지시문·자료실. 스레드는 보통 클라우드 세션이며, 각자 자기 브랜치에서 일하고 필요하면 PR을 엽니다. 사실
  2. 어디서·누가: Pro·Max 공개 베타, 단계적 배포 중. claude.ai/code, 데스크톱 앱 Code 탭, Claude 모바일 앱에서 사용. 터미널 CLI·VS Code·JetBrains에서는 쓸 수 없고, Team·Enterprise는 아직 미지원. 사이드바에 Projects가 없으면 아직 내 계정에 배포되지 않은 것입니다(대기자 명단 있음). 사실
  3. 언제: 한 세션으로 끝나지 않고 계속 작업이 생기는 목표(여러 저장소에 같은 변경, 계속 들어오는 버그, 큰 빌드·마이그레이션, 반복 질문하는 문서 묶음). 작업 하나면 그냥 클라우드 세션이 낫습니다. 사실
  4. 비용: 일반 세션과 같은 요금제 한도를 쓰되 더 빨리 씁니다. 새 프로젝트의 기본값은 스레드 Opus·high라 가장 빨리 닳으므로, 처음에 스레드 모델·effort를 조정하고 "동시에 2개까지만" 같은 규칙을 주세요. 사실 + 추론
  5. 기존 Claude 앱의 프로젝트(채팅·Cowork에서 대화와 참고 파일을 묶던 것)는 당분간 그대로 동작하며, 새 방식이 그쪽으로 확대될 때 업그레이드된다고 안내돼 있습니다. 사실

쉽게 이해하기

직관적 설명 (비유): 나는 "의뢰인", 프로젝트 대화의 클로드는 "팀장(코디네이터)", 스레드는 "팀원"입니다. 의뢰인이 메신저 방 하나에 요청을 던지면, 팀장이 일을 쪼개 팀원에게 배정하고, 팀원은 각자 자기 책상(클라우드 샌드박스와 브랜치)에서 일한 뒤 결과를 보고합니다. 팀 공용 노트(프로젝트 메모리)와 자료실(Library)이 있어, 한 번 정한 규칙은 다음 팀원도 압니다.

실제 구조 사실: 코디네이터는 스레드의 모든 단계를 보지 않고 스레드가 보고한 내용만 봅니다. 스레드는 각자 컨텍스트 창을 가진 별개의 세션이므로 서로의 대화를 공유하지 않으며, 공유되는 것은 프로젝트 지시문·메모리·저장소·파일·환경입니다. 프로젝트 대화는 전체 기록 대신 최근 메시지, 최근 스레드, 프로젝트 메모리로 일하기 때문에 컨텍스트를 직접 관리할 필요가 없습니다.

PR 흐름

클라우드 스레드는 기본 브랜치에서 새 브랜치를 만들어 일하고, 요청하면(또는 버그 수정 같은 구체적 변경이면 스스로) PR을 엽니다. PR을 연 뒤에는 auto-fix를 켠 채 감시하며 CI 실패를 고치고, 리뷰 코멘트에 대응하고, 준비되면 알려 줍니다. 스레드 카드에는 Resolve conflicts, Fix CI, Address comments, Merge it(그 지시를 내 메시지로 스레드에 전달), Review PR(GitHub에서 열기), Create PR(푸시만 하고 PR이 없을 때 바로 생성) 버튼이 나타납니다. 사실

한계와 문제 해결 사실

  • 프로젝트는 한 사용자 소유입니다. 공유할 수 없고, 스레드 기록에는 다른 클라우드 세션에 있는 공유 옵션이 없습니다. 베타 기간에는 조직 관리 기능이 없습니다.
  • 스레드는 만든 프로젝트에 속하며 다른 프로젝트로 옮기거나 떼어낼 수 없고, 두 프로젝트를 합칠 수 없습니다.
  • 클라우드 스레드의 샌드박스는 턴 사이에 일시 정지됩니다. 재개에 실패하면 새로 클론해 이어 가므로 커밋하지 않은 변경이 사라질 수 있습니다. 긴 작업은 "진행분을 커밋하고 푸시해"라고 지시하세요.
  • Amazon Bedrock·Google Cloud·Microsoft Foundry로는 쓸 수 없습니다(모델 제공처는 Anthropic).

결론

클로드는 답을 주는 기계가 아니라 질문하고, 확인하고, 피드백하는 튜터로 쓸 때 실력이 붙습니다. 원칙은 세 가지입니다. ① 내가 먼저 떠올리고 답한다(인출 연습), ② 틀린 부분을 설명으로 교정받는다, ③ 간격을 두고 다시 확인한다. 그리고 버전에 따라 바뀌는 메뉴·기능은 반드시 공식 문서로 확인합니다. 추론 (학습법 일반)

외국어

  1. 입력
    수준에 맞춘 읽기 자료"내 수준(B1)에 맞춰 이 기사를 300단어로 다시 써 주고, 새 단어 10개에 예문을 붙여 줘." 원문 기사는 내가 가져옵니다.
  2. 출력
    쓰기 교정"내 글을 고치되, 고친 이유를 문법 규칙 이름과 함께 표로. 자연스럽지만 틀리지 않은 표현은 고치지 말고 '대안'으로만."
  3. 대화
    상황극"카페 주문 상황에서 직원 역할을 해. 내가 실수하면 대화를 멈추지 말고, 끝난 뒤 실수 목록을 줘."
  4. 복습
    오답 노트매 세션 끝에 "오늘 내 실수 패턴 3가지와 다음 연습 과제"를 받아 저장.
한계. 클로드에 음성 모드가 있지만, 발음을 얼마나 정확하게 평가할 수 있는지는 공식 자료에서 확인하지 못했습니다. 발음은 원어민 음성 자료나 전문 서비스와 병행하세요. 사전·문법서 수준의 정확성이 필요하면 공인 사전으로 교차 확인합니다.

코딩·프로그래밍

  • 복붙 대신 손으로: /output-style learning을 켜고 실제 프로젝트를 진행하면 핵심 결정을 내가 쓰게 됩니다.
  • 코드 읽기 질문: 공식 문서는 낯선 코드베이스 온보딩에 "선배 엔지니어에게 묻듯 질문하라"고 권합니다. 예: "134번째 줄의 async move { ... }는 무엇을 하나?", "이 코드는 왜 bar() 대신 foo()를 부르나?" 사실
  • 디버깅은 가설부터: "답을 주지 말고, 내가 원인을 찾도록 확인해 볼 지점을 순서대로 질문해 줘."
  • 내 코드 리뷰받기: "시니어 리뷰어처럼 심각도별로 지적하고, 각 항목에 왜 문제인지와 더 나은 예를 줘."
  • 작지만 진짜인 프로젝트: 할 일 앱보다 내가 실제로 쓸 도구(파일 이름 일괄 변경기, 개인 가계부 CSV 분석기)가 동기 유지에 유리합니다. 추론
  • 테스트로 이해 확인: 함수를 설명받은 뒤 그 함수의 테스트를 내가 먼저 써 보고 클로드에게 빠진 경우를 묻습니다.

애프터 이펙트 After Effects

클로드가 잘 도와줄 수 있는 영역은 익스프레션(JavaScript 기반 식), 스크립트(ExtendScript, .jsx), 그리고 원리 설명입니다. 반면 클로드는 애프터 이펙트를 직접 실행하거나 화면을 볼 수 없으므로(스크린샷을 주면 볼 수 있음), 결과 확인은 내가 합니다. 추론

After Effects [버전]을 쓰고 있어. 익스프레션 엔진은 JavaScript로 설정돼 있어.

  • 스크립트 자동화: 반복 작업(레이어 이름 일괄 변경, 컴프 일괄 생성)은 .jsx 스크립트로 요청하고, 복사본 프로젝트에서 먼저 실행합니다.
정확성 주의. AE의 메뉴 경로, 패널 이름, 단축키는 버전에 따라 바뀝니다. 클로드의 지식에는 날짜 한계가 있으므로 버전을 꼭 알려 주고, 틀린 안내를 발견하면 Adobe 공식 도움말로 확인하세요.

블렌더 Blender

요청하신 "블렌딩"을 3D 프로그램 블렌더로 해석해 정리했습니다(합성의 블렌딩 모드는 위 AE 항목에 있습니다). 블렌더는 Python API(bpy)가 있어 클로드와 가장 잘 맞는 창작 도구 중 하나입니다. 추론

  • 스크립트로 배우기: "UI로 하는 방법과 같은 일을 하는 bpy 코드를 둘 다 보여 줘." 두 가지를 대조하면 구조(오브젝트, 메시 데이터, 모디파이어)가 보입니다.
  • 클로드 코드로 자동화: 블렌더가 설치된 내 컴퓨터에서 클로드 코드를 쓰면, 클로드가 스크립트를 작성하고 백그라운드 모드로 실행해 결과(로그, 렌더 이미지)를 확인하게 할 수 있습니다.
블렌더 화면 없이 스크립트 실행 (블렌더 CLI)
blender --background --python make_scene.py
# 특정 .blend 파일을 열고 실행
blender --background scene.blend --python render_check.py

- 1280x720 PNG 한 장을 renders/test.png 로 렌더
blender --background --python make_scene.py 로 실행해서
오류가 없는지 로그를 확인하고, 렌더 이미지를 열어 구도를 점검해.
bpy API가 버전에 따라 다르면 내 버전 기준으로 맞추고 차이를 알려 줘.
  • 지오메트리 노드: 노드 그래프는 말로 설명하기 어려우므로 노드 에디터 스크린샷을 주고 "이 그래프가 하는 일을 순서대로 설명해 줘"가 효과적입니다.
  • 렌더 설정: "Cycles와 EEVEE 중 이 장면에 맞는 것과 이유", "노이즈를 줄이는 설정 우선순위"처럼 판단 기준을 물으세요.
정확성 주의. bpy API와 UI는 버전에 따라 이름이 바뀐 사례가 있습니다. 실행 오류가 나면 오류 메시지 전체를 붙여 주고, 공식 Blender Python API 문서로 확인하세요. 스크립트는 저장되지 않은 작업이 없는 상태나 복사본에서 실행합니다.
